PortfolioOS — working flow

What is actually running: one login page, one API, Postgres, and an optional WhatsApp path through Qlix adk_new. Same product, one file.

People

Browser or WhatsApp

Thyagu (owner), 7 managers, SCALE vice manager, TMS team lead, team members. Dashboard is localhost:3001. WhatsApp hits the gateway on :3938.

Web

Next.js dashboard

One route: /. Login posts email and password. After login the page shows organisations. Owners also see readiness.

API

Node API :4001

JWT identifies a membership. Every query sets app.role, app.org_id, app.membership_id so Postgres row security can apply.

Data

Postgres :5433

7 organisations, 32 people, 61 KPIs. Submissions, sign-off, scores, and agent tool calls live here. Docker, not the Mac Postgres on 5432.

WhatsApp does not talk to the database. It goes gateway → agent-runner (:3940) → adk_new → the same API.

Transport

WA gateway

Looks up the phone, picks the agent, queues the reply. Running in stub mode (WA_DISABLE=1) so messages are logged, not sent on WhatsApp.

Bridge

Agent runner

Asks the API for a short-lived run token, then starts the Python handler in qlix-monorepo/adk_new.

Agent

portfolio_os tools

Readiness, KPI, pending, submit, and (owner only, with confirm) target updates. Tools call POST /agent/tools/portfolio_os.

Same lock

One permission point

The model never holds a database password. A manager asking about another organisation gets nothing, because the API never queries outside their org.

There is no /owner or /portfolio route yet. The difference is what the API returns after the same login page.

Member submits a number

Example: Sasikumar posts sai.mentor_sessions = 3 for today. API writes a submission in state submitted. Channel is web or later whatsapp.

Lead accepts or rejects

Nagaraj does not overwrite the number. Accept moves it to validated. Reject sends it back with a reason.

Lead signs off the day

POST /orgs/sai/signoff locks validated rows for that date. After lock, a correction is an amendment, not an edit.

Scores appear

If the KPI has a target and thresholds: green, amber, or red. If the target is still empty (50 of 61 at seed): unscored. The dashboard is meant to show readiness, not a fake green.

Go-live for one organisation

No unnamed people, every KPI has a target or is marked unmeasured by Thyagu, and one full day has been locked. SAI is the pilot because both people are already named.

Deadlines in the spec (Asia/Kolkata): members 17:00, team lead / vice manager 18:00, managers 19:00. The running app stores the data; the clock nudges are not sending yet.

Message arrives

Gateway normalises the phone to E.164 and looks up users.phone_e164. No match: one reply, “not registered”, and stop. Seed data has no phone numbers yet, so this path is closed until numbers are collected.

Agent is chosen before the model runs

Owner → portfolio-owner-agent. Everyone else → portfolio-reporter-agent. A morning digest uses portfolio-digest-agent (read only).

adk_new calls the API

Typical owner question “readiness” calls get_readiness. “kpi sai.incubated” calls get_kpi. Writes such as changing a target return a preview and need a second confirm. That check is in the API, not only in the prompt.

Reply is queued

Text goes into wa_outbox. The gateway drains the queue. In the current run it uses a stub sender, so nothing leaves the machine.
